## 15에서 16으로 업그레이드

### Next.js DevTools MCP와 함께 AI 에이전트 사용

If you're using an AI coding assistant that supports the [MCP(모델 컨텍스트 프로토콜)](https://modelcontextprotocol.io)를 지원하는 AI 코딩 도우미를 사용하는 경우 **Next.js DevTools MCP**를 사용하여 업그레이드 프로세스 및 마이그레이션 작업을 자동화할 수 있습니다.

#### 설정

MCP 클라이언트에 다음 구성을 추가합니다. 각 코딩 에이전트에 대해 [이 섹션](https://github.com/vercel/next-devtools-mcp#mcp-client-configuration)에서 구성 세부 정보를 확인할 수 있습니다.

**예:**

```json filename=".mcp.json"
{
  "mcpServers": {
    "next-devtools": {
      "command": "npx",
      "args": ["-y", "next-devtools-mcp@latest"]
    }
  }
}
```

자세한 내용은 [`next-devtools-mcp`](https://github.com/vercel/next-devtools-mcp) 설명서를 참조하여 MCP 클라이언트로 구성하세요.

> **참고:** `next-devtools-mcp@latest`를 사용하면 MCP 클라이언트가 항상 Next.js DevTools MCP 서버의 최신 버전을 사용하게 됩니다.

#### 프롬프트 예

구성한 후에는 자연어 프롬프트를 사용하여 Next.js 앱을 업그레이드할 수 있습니다.

**Next.js 16으로 업그레이드하려면:**

코딩 에이전트에 연결한 후 다음 메시지를 표시합니다.

```txt
Next Devtools, help me upgrade my Next.js app to version 16
```

**캐시 구성 요소로 마이그레이션하려면(v16으로 업그레이드한 후):**

코딩 에이전트에 연결한 후 다음 메시지를 표시합니다.

```txt
Next Devtools, migrate my Next.js app to cache components
```

Learn more in the documentation [여기](../mcp.mdx) 문서에서 자세히 알아보세요.

### Codemod 사용하기

Next.js 버전 16으로 업데이트하려면 `upgrade` [codemod](codemods.mdx#160)를 사용할 수 있습니다.

```bash filename="Terminal"
npx @next/codemod@canary upgrade latest
```

The [codemod](codemods.mdx#160)는 다음을 수행할 수 있습니다.

- 새로운 `next.config.js` 구성을 사용하려면 `turbopack`을 업데이트하세요.
- Migrate from `next lint`에서 ESLint CLI로 마이그레이션
- 더 이상 사용되지 않는 `middleware` 규칙을 `proxy`
- 안정화된 API에서 `unstable_` 접두사 제거
- 페이지 및 레이아웃에서 `experimental_ppr` 경로 세그먼트 구성을 제거합니다.

수동으로 수행하려면 최신 Next.js 및 React 버전을 설치하세요.

```bash filename="Terminal"
npm install next@latest react@latest react-dom@latest
```

TypeScript를 사용하는 경우 `@types/react` 및 `@types/react-dom`도 최신 버전으로 업그레이드하세요.

## Turbopack 기본적으로

Starting with **Next.js 16**부터 Turbopack는 안정적이며 기본적으로 `next dev` 및 `next build`

이전에는 `--turbopack` 또는 `--turbo`을 사용하여 Turbopack를 활성화해야 했습니다.

```json filename="package.json"
{
  "scripts": {
    "dev": "next dev --turbopack",
    "build": "next build --turbopack",
    "start": "next start"
  }
}
```

더 이상 필요하지 않습니다. `package.json` 스크립트를 업데이트할 수 있습니다.

```json filename="package.json"
{
  "scripts": {
    "dev": "next dev",
    "build": "next build",
    "start": "next start"
  }
}
```

프로젝트에 [사용자 정의 `webpack`](../../api-reference/config/next-config-js/webpack.mdx) 구성이 있고 `next build`(현재 기본적으로 Turbopack 사용)을 실행하는 경우 잘못된 구성 문제를 방지하기 위해 빌드가 **실패**합니다.

이 문제를 해결하는 몇 가지 방법이 있습니다.

- **어쨌든 Turbopack를 사용하세요.** Turbopack를 사용하여 빌드하려면 `next build --turbopack`로 실행하고 `webpack` 구성을 무시하세요.
- **Turbopack로 완전히 전환:** `webpack` 구성을 Turbopack 호환 옵션으로 마이그레이션합니다.
- **Webpack를 계속 사용하세요.** Turbopack를 선택 해제하고 Webpack를 사용하여 빌드하려면 `--webpack` 플래그를 사용하세요.

> **알아두면 좋은 정보**: `webpack` 구성이 발견되어 빌드 실패가 표시되지만 직접 정의하지 않은 경우 플러그인이 `webpack` 옵션을 추가하고 있을 가능성이 높습니다.

### Turbopack 선택 해제

Webpack를 계속 사용해야 하는 경우 `--webpack` 플래그를 사용하여 선택 해제할 수 있습니다. 예를 들어 개발에서는 Turbopack를 사용하고 프로덕션 빌드에서는 Webpack를 사용하려면 다음을 수행하세요.

```json filename="package.json"
{
  "scripts": {
    "dev": "next dev",
    "build": "next build --webpack",
    "start": "next start"
  }
}
```

개발 및 프로덕션에는 Turbopack를 사용하는 것이 좋습니다. Turbopack로 전환할 수 없는 경우 이 [스레드](https://github.com/vercel/next.js/discussions/77721)에 의견을 제출하세요.


### 별칭 폴백 해결

일부 프로젝트에서는 클라이언트측 코드가 Node.js 네이티브 모듈이 포함된 파일을 가져올 수 있습니다. 이로 인해 `Module not found: Can't resolve 'fs'` 유형의 오류가 발생합니다.

이런 일이 발생하면 클라이언트측 번들이 이러한 Node.js 네이티브 모듈을 참조하지 않도록 코드를 리팩터링해야 합니다.

그러나 어떤 경우에는 이것이 불가능할 수도 있습니다. Webpack에서 `resolve.fallback` 옵션은 일반적으로 오류를 **무음**하는 데 사용되었습니다. Turbopack는 `turbopack.resolveAlias`을 사용하여 유사한 옵션을 제공합니다. 이 경우 브라우저에 `fs`이 요청되면 빈 모듈을 로드하도록 Turbopack에 지시합니다.

```ts filename="next.config.ts"
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  turbopack: {
    resolveAlias: {
      fs: {
        browser: './empty.ts', // We recommend to fix code imports before using this method
      },
    },
  },
}

export default nextConfig
```

클라이언트 코드가 Node.js 기본 모듈을 사용하는 모듈에서 가져오지 않도록 모듈을 리팩터링하는 것이 좋습니다.

### Sass node\_modules 가져오기Turbopack는 에서 Sass 파일 가져오기를 완벽하게 지원합니다. Webpack에서는 기존 물결표() 접두사를 허용했지만 Turbopack에서는 이 구문을 지원하지 않습니다.

Webpack에서:`node_modules`. Note that while Webpack allowed the legacy tilde (`~`) prefix, Turbopack does not support this syntax.

Turbopack에서:

```scss filename="styles/globals.scss"
@import '~bootstrap/dist/css/bootstrap.min.css';
```

가져오기를 변경할 수 없는 경우 을 사용할 수 있습니다. 예를 들면:

```scss filename="styles/globals.scss"
@import 'bootstrap/dist/css/bootstrap.min.css';
```

Turbopack는 이제 개발 시 파일 시스템 캐싱을 지원하여 실행 간 디스크에 컴파일러 아티팩트를 저장하여 다시 시작할 때 컴파일 시간이 훨씬 빨라집니다.`turbopack.resolveAlias`. For example:

```ts filename="next.config.ts"
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  turbopack: {
    resolveAlias: {
      '~*': '*',
    },
  },
}

export default nextConfig
```

- [`PageProps`](../../api-reference/file-conventions/page.mdx#page-props-helper)
- [`LayoutProps`](../../api-reference/file-conventions/layout.mdx#layout-props-helper)
- [`RouteContext`](../../api-reference/file-conventions/route.mdx#route-context-helper)

> **알아두면 좋은 점:** React 컴파일러는 Babel를 사용하므로 이 옵션을 활성화하면 개발 및 빌드 중에 컴파일 시간이 더 길어질 수 있습니다.`typegen` was introduced in Next.js 15.5

This simplifies type-safe migration to the new async API pattern, and enables you to update your components with full type safety, for example:에 새로운 함수 서명이 있습니다.  프로필을 두 번째 인수로 전달할 수 있습니다.

```tsx filename="/app/blog/[slug]/page.tsx"

  const query = await props.searchParams
```

블로그 게시물, 제품 카탈로그, 문서 등 업데이트가 약간 지연될 수 있는 콘텐츠에는 `props.params`을 사용하세요. 사용자는 백그라운드에서 새로운 데이터가 로드되는 동안 오래된 콘텐츠를 받습니다.`slug`, and to `searchParams`, directly within your page.

## Async parameters for icon, and open-graph Image (Breaking change)

> The props passed to the image generating functions in `opengraph-image`, `twitter-image`, `icon`, and `apple-icon`, are now Promises.

In previous versions, both the `Image` (image generation function), and the `generateImageMetadata` received a `params` object. The `id` returned by `generateImageMetadata` was passed as a string to the image generation function.는 사용자가 변경하면 오래된 데이터가 아닌 UI에 변경 사항이 즉시 표시되는  의미 체계를 제공하는 새로운  전용 API입니다.

```js filename="app/shop/[slug]/opengraph-image.js"
// Next.js 15 - synchronous params access
export function generateImageMetadata({ params }) {
  const { slug } = params
  return [{ id: '1' }, { id: '2' }]
}

// Next.js 15 - synchronous params and id access
export default function Image({ params, id }) {
  const slug = params.slug
  const imageId = id // string
  // ...
}
```

이렇게 하면 대화형 기능이 변경 사항을 즉시 반영할 수 있습니다. 사용자가 업데이트를 즉시 확인하기를 원하는 양식, 사용자 설정 및 모든 워크플로에 적합합니다.**Next.js 16**, to align with the [Async Request APIs](#async-request-apis-breaking-change) change, the image generating function now receives `params` and `id` as promises. The `generateImageMetadata` function continues to receive synchronous `params`.

```js filename="app/shop/[slug]/opengraph-image.js"
export async function generateImageMetadata({ params }) {
  const { slug } = params
  return [{ id: '1' }, { id: '2' }]
}

// Next.js 16 - asynchronous params and id access
export default async function Image({ params, id }) {
  const { slug } = await params // params now async
  const imageId = await id // id is now Promise<string> when using generateImageMetadata
  // ...
}
```

## Async `id` parameter for `sitemap` (Breaking change)

작업을 수행한 후 클라이언트 라우터를 새로 고쳐야 할 때 사용합니다.`id` values returned from [`generateSitemaps`](../../api-reference/functions/generate-sitemaps.mdx) were passed directly to the `sitemap` generating function.

```js filename="app/product/sitemap.js"
export async function generateSitemaps() {
  return [{ id: 0 }, { id: 1 }, { id: 2 }, { id: 3 }]
}

// Next.js 15 - synchronous id access
export default async function sitemap({ id }) {
  const start = id * 50000 // id is a number
  // ...
}
```

가져오기를 다음으로 업데이트할 수 있습니다.**Next.js 16**, the `sitemap` generating function now receives `id` as a promise.

```js filename="app/product/sitemap.js"
export async function generateSitemaps() {
  return [{ id: 0 }, { id: 1 }, { id: 2 }, { id: 3 }]
}

// Next.js 16 - asynchronous id access
export default async function sitemap({ id }) {
  const resolvedId = await id // id is now Promise<string>
  const start = Number(resolvedId) * 50000
  // ...
}
```

## 향상된 라우팅 및 탐색

The App Router in **Next.js 16**에는 경로 지정 및 탐색 시스템이 완전히 정비되어 페이지 전환이 더 간결하고 빨라졌습니다. 이는 Next.js가 탐색 데이터를 미리 가져오고 캐시하는 방법을 최적화합니다.[Canary release](https://react.dev/blog/2023/05/03/react-canaries), which includes the newly released React 19.2 features and other features being incrementally stabilized. Highlights include:

- **[View Transitions](https://react.dev/reference/react/ViewTransition)**: 공유 레이아웃이 포함된 여러 URL를 미리 가져오는 경우 레이아웃이 한 번 다운로드됩니다.
- **[`useEffectEvent`](https://react.dev/reference/react/useEffectEvent)**: Next.js는 전체 페이지가 아닌 아직 캐시에 없는 부분만 프리페치합니다.
- **[Activity](https://react.dev/reference/react/Activity)**: Render "background activity" by hiding UI with `display: none` while maintaining state and cleaning up Effects

이러한 변경 사항에는 [React 19.2 announcement](https://react.dev/blog/2025/10/01/react-19-2). 모든 앱의 성능을 향상시키도록 설계되었습니다.

## 부분 사전 렌더링(PPR)

Built-in support for the React Compiler is now stable in **Next.js 16**은 경로 수준 세그먼트 을 포함하여 실험적인  플래그 및 구성 옵션을 제거합니다.

The `reactCompiler` configuration option has been promoted from `experimental` to stable. It is not enabled by default as we continue gathering build performance data across different application types.부터  구성을 사용하여 PPR를 선택할 수 있습니다.

```ts filename="next.config.ts" switcher
  reactCompiler: true,

```

```js filename="next.config.js" switcher

  reactCompiler: true,
}
```


## Enhanced Routing and Navigation

**Next.js 16** includes a complete overhaul of the routing and navigation system, making page transitions leaner and faster. This optimizes how Next.js prefetches and caches navigation data:의 기본값이 무제한에서 최대 3개의 리디렉션으로 변경되었습니다.

- **Layout deduplication**: When prefetching multiple URLs with a shared layout, the layout is downloaded once.
- **Incremental prefetching**: Next.js only prefetches parts not already in cache, rather than entire pages.

These changes require **no code modifications** and are designed to improve performance across all apps. 구성 요소는 더 이상 사용되지 않습니다. 대신 을 사용하세요.

However, you may see more individual prefetch requests with much lower total transfer sizes. We believe this is the right trade-off for nearly all applications. 구성은 더 이상 사용되지 않습니다.

보안을 강화하려면 대신 [issue](https://github.com/vercel/next.js/issues) or [discussion](https://github.com/vercel/next.js/discussions) item.을 사용하세요.

### `minimumCacheTTL` Default (Breaking change)

The default value for `images.minimumCacheTTL` 및 `60 seconds`이 제거되었습니다. 대신 환경 변수를 사용하세요.`4 hours` (14400 seconds). This reduces revalidation cost for images without cache-control headers.

For some Next.js users, image revalidation was happening frequently, often because the upstream source images missed a `cache-control` header. This caused revalidation to happen every `60` seconds, which increased CPU usage and cost.

Since most images do not change often, this short interval is not ideal. Setting the default to 4 hours offers a more durable cache by default, while still allowing images to update a few times per day if needed.

## Scroll Behavior Override

In **previous versions of Next.js**, if you had set `scroll-behavior: smooth` globally on your `<html>` element via CSS, Next.js would override this during SPA route transitions, as follows:

1. Temporarily set `scroll-behavior` to `auto`
1. Perform the navigation (causing instant scroll to top)
1. Restore your original `scroll-behavior` value

This ensured that page navigation always felt snappy and instant, even when you had smooth scrolling enabled for in-page navigation. However, this manipulation could be expensive, especially at the start of every navigation.

In **Next.js 16**, this behavior has changed. By default, Next.js will **no longer override** your `scroll-behavior` setting during navigation.

**If you want Next.js to perform this override** (the previous default behavior), add the `data-scroll-behavior="smooth"` attribute to your `<html>` element:

```tsx filename="app/layout.tsx"
export default function RootLayout({ children }) {
  return (
    <html lang="en" data-scroll-behavior="smooth">
      <body>{children}</body>
    </html>
  )
}
```

## Performance Improvements

Significant performance optimizations for `next dev` and `next start` commands, along with improved terminal output with clearer formatting, better error messages, and improved performance metrics.

**Next.js 16** removes the `size` and `First Load JS` metrics from the `next build` output. We found these to be inaccurate in server-driven architectures using React Server Components. Both our Turbopack and Webpack implementations had issues, and disagreed on how to account for Client Components payload.

The most effective way to measure actual route performance is through tools such as [Chrome Lighthouse](https://developer.chrome.com/docs/lighthouse/overview) or Vercel Analytics, which focus on Core Web Vitals and downloaded resource sizes.

### `next dev` config load

In previous versions the Next config file was loaded twice during development:

- When running the `next dev` command
- When the `next dev` command started the Next.js server

This was inefficient because the `next dev` command doesn't need the config file to start the Next.js server.

A consequence of this change is that, when running `next dev` checking if `process.argv` includes `'dev'`, in your Next.js config file, will return `false`.

> **Good to know**: The `typegen`, and `build` commands, are still visible in `process.argv`.

This is specially important for plugins that trigger side-effects on `next dev`. If that's the case, it might be enough to check if `NODE_ENV` is set to `development`.

```js filename="next.config.js"
import { startServer } from 'docs-lib/dev-server'

const isDev = process.env.NODE_ENV === 'development'

if (isDev) {
  startServer()
}

const nextConfig = {
  /* Your config options */
}

module.exports = nextConfig
```

Alternatively, use the [`phase`](../../api-reference/config/next-config-js/index.mdx#phase) in which the configuration is loaded.

```js filename="next.config.js"
module.exports = {
  serverRuntimeConfig: {
    dbUrl: process.env.DATABASE_URL,
  },
  publicRuntimeConfig: {
    apiUrl: '/api',
  },
}
```

```tsx filename="pages/index.tsx"
import getConfig from 'next/config'

export default function Page() {
  const { publicRuntimeConfig } = getConfig()
  return <p>API URL: {publicRuntimeConfig.apiUrl}</p>
}
```

**After (Next.js 16):**

For server-only values, access environment variables directly in Server Components:

```tsx filename="app/page.tsx"
async function fetchData() {
  const dbUrl = process.env.DATABASE_URL
  // Use for server-side operations only
  return await db.query(dbUrl, 'SELECT * FROM users')
}

export default async function Page() {
  const data = await fetchData()
  return <div>{/* render data */}</div>
}
```

> **Good to know**: Use the [taint API](../../api-reference/config/next-config-js/taint.mdx) to prevent accidentally passing sensitive server values to Client Components.

For client-accessible values, use the `NEXT_PUBLIC_` prefix:

```bash filename=".env.local"
NEXT_PUBLIC_API_URL="/api"
```

```tsx filename="app/components/client-component.tsx"
'use client'

export default function ClientComponent() {
  const apiUrl = process.env.NEXT_PUBLIC_API_URL
  return <p>API URL: {apiUrl}</p>
}
```

To ensure environment variables are read at runtime (not bundled at build time), use the [`connection()`](../../api-reference/functions/connection.mdx) function before reading from `process.env`:

```tsx filename="app/page.tsx"
import { connection } from 'next/server'

export default async function Page() {
  await connection()
  const config = process.env.RUNTIME_CONFIG
  return <p>{config}</p>
}
```

Learn more about [environment variables](../environment-variables.mdx).

### `devIndicators` Options

The following options have been removed from [`devIndicators`](../../api-reference/config/next-config-js/devIndicators.mdx):

- `appIsrStatus`
- `buildActivity`
- `buildActivityPosition`

The indicator itself remains available.

### `experimental.dynamicIO`

The `experimental.dynamicIO` flag has been renamed to `cacheComponents`:

Update your Next config file, by removing the `dynamicIO` flag.

```js filename="next.config.js"
// Next.js 15 - experimental.dynamicIO is now removed
module.exports = {
  experimental: {
    dynamicIO: true,
  },
}
```

Add the [`cacheComponents`](../../api-reference/config/next-config-js/cacheComponents.mdx) flag set to true.

```js filename="next.config.js"
// Next.js 16 - use cacheComponents instead
module.exports = {
  cacheComponents: true,
}
```

### `unstable_rootParams`

The `unstable_rootParams` function has been removed. We are working on an alternative API that we will ship in an upcoming minor release.
