애플리케이션이 성장하고 기능이 더욱 풍부해짐에 따라 로컬에서 개발하거나 프로덕션 빌드를 생성할 때 더 많은 리소스가 필요할 수 있습니다.

Next.js에서 메모리를 최적화하고 일반적인 메모리 문제를 해결하기 위한 몇 가지 전략과 기술을 살펴보겠습니다.

## 의존성 수 줄이기

종속성이 많은 애플리케이션은 더 많은 메모리를 사용합니다.

The [번들 분석기](package-bundling.mdx)는 성능 및 메모리 사용량 개선을 위해 제거할 수 있는 애플리케이션의 대규모 종속성을 조사하는 데 도움이 될 수 있습니다.

## Try `experimental.webpackMemoryOptimizations`

Starting in `v15.0.0`부터 `experimental.webpackMemoryOptimizations: true` 파일에 `next.config.js`을 추가하여 Webpack의 동작을 변경하면 최대 메모리 사용량은 줄어들지만 컴파일 시간은 약간 늘어날 수 있습니다.

> **알아두면 좋은 정보**: 이 기능은 현재 더 많은 프로젝트에서 먼저 테스트하기 위해 실험적이지만 위험도가 낮은 것으로 간주됩니다.

## Run `next build`을 사용하여 `--experimental-debug-memory-usage`

Starting in `14.2.0`부터 `next build --experimental-debug-memory-usage`를 실행하여 Next.js가 힙 사용량 및 가비지 수집 통계와 같이 빌드 전체에서 메모리 사용량에 대한 정보를 지속적으로 인쇄하는 모드에서 빌드를 실행할 수 있습니다. 메모리 사용량이 구성된 제한에 가까워지면 힙 스냅샷도 자동으로 생성됩니다.

> **알아두면 좋은 정보**: 이 기능은 사용자 정의 웹팩 구성이 없으면 자동으로 활성화되는 Webpack 빌드 작업자 옵션과 호환되지 않습니다.

## 힙 프로필 기록

메모리 문제를 찾으려면 Node.js에서 힙 프로필을 기록하고 Chrome DevTools에 로드하여 메모리 누수의 잠재적 원인을 식별할 수 있습니다.

터미널에서 Next.js 빌드를 시작할 때 `--heap-prof` 플래그를 Node.js에 전달합니다.

```sh
node --heap-prof node_modules/next/dist/bin/next build
```

빌드가 끝나면 `.heapprofile` 파일이 Node.js에 의해 생성됩니다.

Chrome DevTools에서 메모리 탭을 열고 "프로필 로드" 버튼을 클릭하여 파일을 시각화할 수 있습니다.

## 힙의 스냅샷 분석

검사기 도구를 사용하여 애플리케이션의 메모리 사용량을 분석할 수 있습니다.

When running the `next build` 또는 `next dev` 명령을 실행할 때 명령 시작 부분에 `NODE_OPTIONS=--inspect`을 추가하세요. 그러면 기본 포트에 검사기 에이전트가 노출됩니다.
사용자 코드가 시작되기 전에 중단하려면 대신 `--inspect-brk`을 전달하면 됩니다. 프로세스가 실행되는 동안 Chrome DevTools와 같은 도구를 사용하여 디버깅 포트에 연결하여 힙의 스냅샷을 기록하고 분석하여 어떤 메모리가 유지되고 있는지 확인할 수 있습니다.

Starting in `14.2.0`부터 `next build` 플래그와 함께 `--experimental-debug-memory-usage`을 실행하면 힙 스냅샷을 더 쉽게 만들 수 있습니다.

이 모드에서 실행하는 동안 언제든지 프로세스에 `SIGUSR2` 신호를 보낼 수 있으며 프로세스는 힙 스냅샷을 생성합니다.힙 스냅샷은 Next.js 애플리케이션의 프로젝트 루트에 저장되며 Chrome DevTools와 같은 모든 힙 분석기에 로드되어 어떤 메모리가 유지되는지 확인할 수 있습니다. 이 모드는 아직 Webpack 빌드 작업자와 호환되지 않습니다.

자세한 내용은 을 참조하세요.

Webpack 빌드 워커를 사용하면 별도의 Node.js 워커 내에서 Webpack 컴파일을 실행할 수 있어 빌드 중에 애플리케이션의 메모리 사용량이 줄어듭니다.[how to record and analyze heap snapshots](https://developer.chrome.com/docs/devtools/memory-problems/heap-snapshots) for more information.

## Webpack 캐시 비활성화

The Webpack build worker allows you to run Webpack compilations inside a separate Node.js worker which will decrease memory usage of your application during builds.는 생성된 Webpack 모듈을 메모리 및/또는 디스크에 저장하여 빌드 속도를 향상시킵니다. 이것은 할 수 있다
성능에 도움이 되지만 캐시된 데이터를 저장하기 위한 애플리케이션의 메모리 사용량도 늘어납니다.

애플리케이션에 `v14.1.0`.을 추가하여 이 동작을 비활성화할 수 있습니다.

유형 검사에는 특히 대규모 프로젝트에서 많은 메모리가 필요할 수 있습니다.
그러나 대부분의 프로젝트에는 이미 이러한 작업을 처리하는 전용 CI 실행기가 있습니다.
빌드에서 "TypeScript 실행" 단계 중에 메모리 부족 문제가 발생하면 빌드 중에 이 작업을 비활성화할 수 있습니다.`experimental.webpackBuildWorker: true` inside your `next.config.js`.

> **알아두면 좋은 정보**: 일부 플러그인은 소스 맵을 켤 수 있으며 비활성화하려면 사용자 정의 구성이 필요할 수 있습니다.## Edge 메모리 문제

## 항목 미리 로드 중

Next.js 서버가 시작되면 요청 시점이 아닌 각 페이지의 JavaScript 모듈을 메모리에 미리 로드합니다.[Webpack cache](https://webpack.js.org/configuration/cache/) saves generated Webpack modules in memory and/or to disk to improve the speed of builds. This can
help with performance, but it will also increase the memory usage of your application to store the cached data.

이 최적화를 통해 초기 메모리 공간이 더 커지는 대신 응답 시간이 더 빨라집니다.[custom Webpack configuration](../api-reference/config/next-config-js/webpack.mdx) to your application:

```js filename="next.config.mjs"
/** @type {import('next').NextConfig} */
const nextConfig = {
  webpack: (
    config,
    { buildId, dev, isServer, defaultLoaders, nextRuntime, webpack }
  ) => {
    if (config.cache && !dev) {
      config.cache = Object.freeze({
        type: 'memory',
      })
    }
    // Important: return the modified config
    return config
  },
}

export default nextConfig
```

## Disable static analysis

Next.js는 이러한 JavaScript 모듈을 언로드하지 않습니다. 즉, 이 최적화가 비활성화된 경우에도 결국 모든 페이지가 요청되면 Next.js 서버의 메모리 공간은 결국 동일하게 됩니다.

```js filename="next.config.mjs"
/** @type {import('next').NextConfig} */
const nextConfig = {
  typescript: {
    // !! WARN !!
    // Dangerously allow production builds to successfully complete even if
    // your project has type errors.
    // !! WARN !!
    ignoreBuildErrors: true,
  },
}

export default nextConfig
```

- [Ignoring TypeScript Errors](../api-reference/config/typescript.mdx#disabling-typescript-errors-in-production)

Keep in mind that this may produce faulty deploys due to type errors.
We strongly recommend only promoting builds to production after static analysis has completed.
If you deploy to Vercel, you can check out the [guide for staging deployments](https://vercel.com/docs/deployments/managing-deployments#staging-and-promoting-a-production-deployment) to learn how to promote builds to production after custom tasks have succeeded.

## Disable source maps

Generating source maps consumes extra memory during the build process.

You can disable source map generation by adding `productionBrowserSourceMaps: false` and `experimental.serverSourceMaps: false` to your Next.js configuration.

When using the `cacheComponents` feature, Next.js will use source maps by default during the prerender phase of `next build`.
If you consistently encounter memory issues during that phase (after "Generating static pages"),
you can try disabling source maps in that phase by adding `enablePrerenderSourceMaps: false` to your Next.js configuration.

> **Good to know**: Some plugins may turn on source maps and may require custom configuration to disable.

## Edge memory issues

Next.js `v14.1.3` fixed a memory issue when using the Edge runtime. Please update to this version (or later) to see if it addresses your issue.

## Preloading Entries

When the Next.js server starts, it preloads each page's JavaScript modules into memory, rather than at request time.

This optimization allows for faster response times, in exchange for a larger initial memory footprint.

To disable this optimization, set the `experimental.preloadEntriesOnStart` flag to `false`.

```ts filename="next.config.ts" switcher
import type { NextConfig } from 'next'

const config: NextConfig = {
  experimental: {
    preloadEntriesOnStart: false,
  },
}

export default config
```

```js filename="next.config.mjs" switcher
/** @type {import('next').NextConfig} */
const config = {
  experimental: {
    preloadEntriesOnStart: false,
  },
}

export default config
```

Next.js doesn't unload these JavaScript modules, meaning that even with this optimization disabled, the memory footprint of your Next.js server will eventually be the same if all pages are eventually requested.
