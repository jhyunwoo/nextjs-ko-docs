이 가이드는 기존 Vite 애플리케이션을 Next.js로 마이그레이션하는 데 도움이 됩니다.

## 스위치를 사용하는 이유는 무엇인가요?

Vite에서 Next.js로 전환하려는 데에는 몇 가지 이유가 있습니다.

### 초기 페이지 로딩 시간이 느림

If you have built your application with the [React용 기본 Vite 플러그인](https://github.com/vitejs/vite-plugin-react/tree/main/packages/plugin-react)을 사용하여 애플리케이션을 구축한 경우 애플리케이션은 순전히 클라이언트측 애플리케이션입니다. SPA(단일 페이지 애플리케이션)라고도 하는 클라이언트측 전용 애플리케이션에서는 초기 페이지 로딩 시간이 느린 경우가 많습니다. 이는 다음과 같은 몇 가지 이유로 인해 발생합니다.

1. 브라우저는 코드가 일부 데이터 로드 요청을 보낼 수 있기 전에 React 코드와 전체 애플리케이션 번들이 다운로드되어 실행될 때까지 기다려야 합니다.
1. 새로운 기능과 추가 종속성을 추가할 때마다 애플리케이션 코드가 늘어납니다.

### 자동 코드 분할 없음

느린 로딩 시간이라는 이전 문제는 코드 분할을 통해 어느 정도 관리할 수 있습니다. 그러나 코드 분할을 수동으로 수행하려고 하면 성능이 저하되는 경우가 많습니다. 수동으로 코드를 분할할 때 실수로 네트워크 워터폴이 발생하기 쉽습니다. Next.js는 라우터에 내장된 자동 코드 분할 기능을 제공합니다.

### 네트워크 폭포수

성능 저하의 일반적인 원인은 애플리케이션이 데이터를 가져오기 위해 순차적으로 클라이언트-서버 요청을 할 때 발생합니다. SPA에서 데이터를 가져오는 일반적인 패턴 중 하나는 처음에 자리 표시자를 렌더링한 다음 구성 요소가 탑재된 후에 데이터를 가져오는 것입니다. 불행하게도 이는 데이터를 가져오는 하위 구성 요소가 상위 구성 요소가 자체 데이터 로드를 완료할 때까지 가져오기를 시작할 수 없음을 의미합니다.

클라이언트에서 데이터 가져오기는 Next.js에서 지원되지만, 데이터 가져오기를 서버로 이동하여 클라이언트-서버 폭포수를 제거할 수 있는 옵션도 제공합니다.

### 빠르고 의도적인 로딩 상태

With built-in support for [React 일시 중단을 통한 스트리밍](../../getting-started/linking-and-navigating.mdx#streaming)에 대한 기본 지원을 사용하면 네트워크 워터폴을 도입하지 않고도 UI의 어느 부분을 먼저 로드할지, 어떤 순서로 로드할지 더욱 의도적으로 설정할 수 있습니다.

이를 통해 [레이아웃 변경](https://vercel.com/blog/how-core-web-vitals-affect-seo)을 더 빠르게 로드하고 제거하는 페이지를 구축할 수 있습니다.

### 데이터 가져오기 전략 선택

필요에 따라 Next.js를 사용하면 페이지 및 구성 요소별로 데이터 가져오기 전략을 선택할 수 있습니다. 빌드 시, 서버 요청 시 또는 클라이언트에서 가져오도록 결정할 수 있습니다. 예를 들어 CMS에서 데이터를 가져와서 빌드 시 블로그 게시물을 렌더링한 다음 CDN에 효율적으로 캐시할 수 있습니다.

### 프록시

[Next.js 프록시](../../api-reference/file-conventions/proxy.mdx)를 사용하면 요청이 완료되기 전에 서버에서 코드를 실행할 수 있습니다. 이는 사용자가 로그인 페이지로 리디렉션되어 인증 전용 페이지를 방문할 때 인증되지 않은 콘텐츠가 깜박이는 것을 방지하는 데 특히 유용합니다. 프록시는 실험과 [국제화](../internationalization.mdx)에도 유용합니다.

### 내장 최적화,  및 는 종종 애플리케이션 성능에 상당한 영향을 미칩니다. Next.js에는 자동으로 최적화하는 구성 요소가 내장되어 있습니다.

[Images](../../api-reference/components/image.mdx), [fonts](../../api-reference/components/font.mdx), and [third-party scripts](../scripts.mdx) often have significant impact on an application's performance. Next.js comes with built-in components that automatically optimize those for you.

### Step 4: Create the Root Layout

The closest equivalent to the root layout file in a Vite application is the
[`index.html` file](https://vitejs.dev/guide/#index-html-and-project-root), which contains your
`<html>`, `<head>`, and `<body>` tags.

```tsx
const App = dynamic(() => import('../../App'), { ssr: false })
```

이제 을 실행하고 을 엽니다. 이제 Next.js에서 실행 중인 애플리케이션을 볼 수 있습니다.

```tsx filename="app/[[...slug]]/page.tsx" switcher
import '../../index.css'
import { ClientOnly } from './client'

export function generateStaticParams() {
  return [{ slug: [''] }]
}

export default function Page() {
  return <ClientOnly />
}
```

```jsx filename="app/[[...slug]]/page.js" switcher
import '../../index.css'
import { ClientOnly } from './client'

export function generateStaticParams() {
  return [{ slug: [''] }]
}

export default function Page() {
  return <ClientOnly />
}
```

### 9단계: 정리

이제 Vite 관련 아티팩트에서 코드베이스를 정리할 수 있습니다.

```tsx filename="App.tsx"
import image from './img.png' // `image` will be '/assets/img.2d8efhg.png' in production

export default function App() {
  return <img src={image} />
}
```

모든 것이 계획대로 진행되었다면 이제 Next.js 애플리케이션이 다음과 같이 작동하고 있는 것입니다.
단일 페이지 애플리케이션. 그러나 귀하는 아직 대부분의 Next.js' 혜택을 활용하고 있지 않으나,
이제 점진적인 변경을 시작하여 모든 이점을 얻을 수 있습니다. 당신이 원하는 것은 다음과 같습니다
다음을 수행:[`<Image>` component](../../api-reference/components/image.mdx), or you can use the object's
`src` property with your existing `<img>` tag.

The `<Image>` component has the added benefits of
[automatic image optimization](../../api-reference/components/image.mdx). The `<Image>`
component automatically sets the `width` and `height` attributes of the resulting `<img>` based on
the image's dimensions. This prevents layout shifts when the image loads. However, this can cause
issues if your app contains images with only one of their dimensions being styled without the other
styled to `auto`. When not styled to `auto`, the dimension will default to the `<img>` dimension
attribute's value, which can cause the image to appear distorted.

Keeping the `<img>` tag will reduce the amount of changes in your application and prevent the above
issues. You can then optionally later migrate to the `<Image>` component to take advantage of optimizing images by [configuring a loader](../../api-reference/components/image.mdx#loader), or moving to the default Next.js server which has automatic image optimization.

1. **Convert absolute import paths for images imported from `/public` into relative imports:**

```tsx
// Before
import logo from '/logo.png'

// After
import logo from '../public/logo.png'
```

2. **Pass the image `src` property instead of the whole image object to your `<img>` tag:**

```tsx
// Before
<img src={logo} />

// After
<img src={logo.src} />
```

Alternatively, you can reference the public URL for the image asset based on the filename. For example, `public/logo.png` will serve the image at `/logo.png` for your application, which would be the `src` value.

> **Warning:** If you're using TypeScript, you might encounter type errors when accessing the `src`
> property. You can safely ignore those for now. They will be fixed by the end of this guide.

### Step 7: Migrate the Environment Variables

Next.js has support for `.env`
[environment variables](../environment-variables.mdx)
similar to Vite. The main difference is the prefix used to expose environment variables on the
client-side.

- React 라우터에서 `VITE_` prefix to `NEXT_PUBLIC_`.로 마이그레이션하면 다음을 얻을 수 있습니다.

Vite exposes a few built-in environment variables on the special `import.meta.env` object which
aren’t supported by Next.js. You need to update their usage as follows:

- `import.meta.env.MODE` ⇒ `process.env.NODE_ENV`
- `import.meta.env.PROD` ⇒ `process.env.NODE_ENV === 'production'`
- `import.meta.env.DEV` ⇒ `process.env.NODE_ENV !== 'production'`
- `import.meta.env.SSR` ⇒ `typeof window !== 'undefined'`

Next.js also doesn't provide a built-in `BASE_URL` environment variable. However, you can still
configure one, if you need it:

1. **Add the following to your `.env` file:**

```bash filename=".env"
# ...
NEXT_PUBLIC_BASE_PATH="/some-base-path"
```

2. **Set [`basePath`](../../api-reference/config/next-config-js/basePath.mdx) to `process.env.NEXT_PUBLIC_BASE_PATH` in your `next.config.mjs` file:**

```js filename="next.config.mjs"
/** @type {import('next').NextConfig} */
const nextConfig = {
  output: 'export', // Outputs a Single-Page Application (SPA).
  distDir: './dist', // Changes the build output directory to `./dist/`.
  basePath: process.env.NEXT_PUBLIC_BASE_PATH, // Sets the base path to `/some-base-path`.
}

export default nextConfig
```

3. **Update `import.meta.env.BASE_URL` usages to `process.env.NEXT_PUBLIC_BASE_PATH`**

### Step 8: Update Scripts in `package.json`

You should now be able to run your application to test if you successfully migrated to Next.js. But
before that, you need to update your `scripts` in your `package.json` with Next.js related commands,
and add `.next` and `next-env.d.ts` to your `.gitignore`:

```json filename="package.json"
{
  "scripts": {
    "dev": "next dev",
    "build": "next build",
    "start": "next start"
  }

```

```txt filename=".gitignore"
# ...
.next
next-env.d.ts
dist
```

Now run `npm run dev`, and open [`http://localhost:3000`](http://localhost:3000). You should see your application now running on Next.js.
