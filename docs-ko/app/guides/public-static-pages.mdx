공개 페이지는 모든 사용자에게 동일한 콘텐츠를 표시합니다. 일반적인 예로는 랜딩 페이지, 마케팅 페이지, 제품 페이지 등이 있습니다.

데이터가 공유되므로 이러한 종류의 페이지는 미리 [사전 렌더링](../glossary.mdx#prerendering)되어 재사용될 수 있습니다. 이로 인해 페이지 로드 속도가 빨라지고 서버 비용이 절감됩니다.

이 가이드에서는 사용자 간에 데이터를 공유하는 공개 페이지를 구축하는 방법을 보여줍니다.

## 예

예를 들어, 제품 목록 페이지를 구축하겠습니다.

정적 헤더로 시작하여 비동기 외부 데이터가 있는 제품 목록을 추가하고 응답을 차단하지 않고 렌더링하는 방법을 알아봅니다. 마지막으로 전체 페이지를 [요청 시간 렌더링](../glossary.mdx#request-time-rendering)으로 전환하지 않고 사용자별 프로모션 배너를 추가하겠습니다.

이 예에 사용된 리소스는 여기에서 찾을 수 있습니다.

- [동영상](https://youtu.be/F6romq71KtI)
- [데모](https://cache-components-public-pages.labs.vercel.dev/)
- [코드](https://github.com/vercel-labs/cache-components-public-pages)

### 1단계: 간단한 헤더 추가

간단한 헤더부터 시작해 보겠습니다.

```tsx filename="app/products/page.tsx"
// Static component
function Header() {
  return <h1>Shop</h1>
}

export default async function Page() {
  return (
    <>
      <Header />
    </>
  )
}
```

#### 정적 구성 요소

The `<Header />` 구성 요소는 외부 데이터, 요청 헤더, 경로 매개변수, 현재 시간 또는 임의 값과 같이 요청 간에 변경되는 입력에 의존하지 않습니다.

출력이 결코 변경되지 않고 미리 결정될 수 있으므로 이러한 종류의 구성 요소를 **정적** 구성 요소라고 합니다. 요청을 기다릴 이유 없이 Next.js는 **사전 렌더링**할 수 있습니다.[build time](../glossary.mdx#build-time).

We can confirm this by running [`next build`](../api-reference/cli/next.mdx#next-build-options)을 실행하여 이를 확인할 수 있습니다.

```bash filename="Terminal"
Route (app)      Revalidate  Expire
┌ ○ /products           15m      1y
└ ○ /_not-found

○  (Static)  prerendered as static content
```

명시적인 구성을 추가하지 않았음에도 불구하고 제품 경로는 정적으로 표시되어 있습니다.

### 2단계: 제품 목록 추가

이제 제품 목록을 가져와서 렌더링해 보겠습니다.

```tsx filename="app/products/page.tsx"
import db from '@/db'
import { List } from '@/app/products/ui'

function Header() {}

// Dynamic component
async function ProductList() {
  const products = await db.product.findMany()
  return <List items={products} />
}

export default async function Page() {
  return (
    <>
      <Header />
      <ProductList />
    </>
  )
}
```

헤더와 달리 제품 목록은 외부 데이터에 따라 달라집니다.

#### 동적 구성요소

이 데이터는 시간이 지남에 따라 **변경될 수** 있으므로 렌더링된 출력이 더 이상 안정적이라고 보장되지 않습니다. 이렇게 하면 제품 목록이 **동적** 구성 요소가 됩니다.

지침이 없으면 프레임워크는 모든 사용자 요청에 대해 **신선한** 데이터를 가져오길 원한다고 가정합니다. 이 디자인 선택은 새 서버 요청이 페이지를 렌더링하는 표준 웹 동작을 반영합니다.

그러나 이 구성 요소가 요청 시 렌더링되는 경우 해당 데이터를 가져오면 **전체** 경로의 응답이 지연됩니다. 페이지를 새로 고치면 이런 일이 발생하는 것을 볼 수 있습니다.

헤더가 즉시 렌더링되더라도 제품 목록 가져오기가 완료될 때까지 브라우저로 보낼 수 없습니다.

이러한 성능 절벽으로부터 우리를 보호하기 위해 Next.js는 우리가 처음으로 [경고](https://nextjs.org/docs/messages/blocking-route)를 표시합니다: **await** data: `Blocking data was accessed outside of Suspense`

이 시점에서 응답을 **차단 해제**하는 방법을 결정해야 합니다. 다음 중 하나:

- [**캐시**](../glossary.mdx#cache-components) 구성요소이므로 **안정**되고 페이지의 나머지 부분과 함께 사전 렌더링될 수 있습니다.
- [**스트림**](../glossary.mdx#streaming)하여 **비차단** 상태가 되고 페이지의 나머지 부분은 이를 기다릴 필요가 없습니다.

우리의 경우 제품 카탈로그는 모든 사용자가 공유하므로 캐싱이 올바른 선택입니다.

### 캐시 구성요소 지시문을 사용하여 함수를 캐시 가능한 것으로 표시할 수 있습니다.

그러면 [`'use cache'`](../api-reference/directives/use-cache.mdx)로 전환됩니다. 처음 실행될 때 우리가 반환하는 것은 무엇이든 캐시되고 재사용됩니다.

```tsx filename="app/products/page.tsx"
import db from '@/db'
import { List } from '@/app/products/ui'

function Header() {}

// Cache component
async function ProductList() {
  'use cache'
  const products = await db.product.findMany()
  return <List items={products} />
}

export default async function Page() {
  return (
    <>
      <Header />
      <ProductList />
    </>
  )
}
```

그러나 페이지가 영원히 정적인 상태로 유지되는 경우는 거의 없습니다.[cache component](../glossary.mdx#cache-components). The first time it runs, whatever we return will be cached and reused.

조만간 간단한 페이지에도 동적 콘텐츠가 필요하게 됩니다. 이를 보여주기 위해 홍보 배너를 추가해 보겠습니다.**before** the request arrives, it can be prerendered just like a static component.

다시 한번, 이것은 역동적으로 시작됩니다. 이전과 마찬가지로 차단 동작을 도입하면 Next.js 경고가 발생합니다.`next build` again, we can confirm the page is still static:

```bash filename="Terminal"
Route (app)      Revalidate  Expire
┌ ○ /products           15m      1y
└ ○ /_not-found

○  (Static)  prerendered as static content
```

폴백은 나머지 정적 및 캐시된 콘텐츠와 함께 사전 렌더링됩니다. 내부 구성 요소는 비동기 작업이 완료되면 나중에 스트리밍됩니다.

### 다음 단계

우리는 동적 콘텐츠가 포함된 대부분 정적인 페이지를 만드는 방법을 배웠습니다.

```tsx filename="app/products/page.tsx"
import db from '@/db'
import { List, Promotion } from '@/app/products/ui'
import { getPromotion } from '@/app/products/data'

function Header() {}

async function ProductList() {}

// Dynamic component
async function PromotionContent() {
  const promotion = await getPromotion()
  return <Promotion data={promotion} />
}

export default async function Page() {
  return (
    <>
      <PromotionContent />
      <Header />
      <ProductList />
    </>
  )
}
```

우리는 정적 페이지로 시작하여 비동기 작업을 추가하고 사전 렌더링할 수 있는 항목을 캐싱하고 렌더링할 수 없는 항목을 스트리밍하여 차단 동작을 해결했습니다.

향후 가이드에서는 다음 방법을 알아봅니다.

### Partial prerendering

Adding dynamic content doesn't mean we have to go back to a fully blocking render. We can unblock the response with streaming.

Next.js supports streaming by default. We can use a [Suspense boundary](../glossary.mdx#suspense-boundary) to tell the framework where to slice the streamed response into *chunks*, and what fallback UI to show while content loads.

```tsx filename="app/products/page.tsx"
import { Suspense } from 'react'
import db from '@/db'
import { List, Promotion, PromotionSkeleton } from '@/app/products/ui'
import { getPromotion } from '@/app/products/data'

function Header() {}

async function ProductList() {}

// Dynamic component (streamed)
async function PromotionContent() {
  const promotion = await getPromotion()
  return <Promotion data={promotion} />
}

export default async function Page() {
  return (
    <>
      <Suspense fallback={<PromotionSkeleton />}>
        <PromotionContent />
      </Suspense>
      <Header />
      <ProductList />
    </>
  )
}
```

The fallback is prerendered alongside the rest of our static and cached content. The inner component streams in later, once its async work completes.

With this change, Next.js can separate prerenderable work from request-time work and the route becomes [partially prerendered](../glossary.mdx#partial-prerendering-ppr).

Again, we can confirm this by running `next build`:

```bash filename="Terminal"
Route (app)      Revalidate  Expire
┌ ◐ /products    15m      1y
└ ◐ /_not-found

◐  (Partial Prerender)  Prerendered as static HTML with dynamic server-streamed content
```

At [**build time**](../glossary.mdx#build-time), most of the page, including the header, product list and promotion fallback, is rendered, cached and pushed to a content delivery network.

At [**request time**](../glossary.mdx#request-time), the prerendered part is served instantly from a CDN node close to the user.

In parallel, the user specific promotion is rendered on the server, streamed to the client, and swapped into the fallback slot.

If we refresh the page one last time, we can see most of the page loads instantly, while the dynamic parts stream in as they become available.
