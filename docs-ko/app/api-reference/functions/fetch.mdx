Next.js는 [웹 `fetch()` API](https://developer.mozilla.org/docs/Web/API/Fetch_API)을 확장하여 서버의 각 요청이 고유한 영구 캐싱 및 재검증 의미 체계를 설정할 수 있도록 합니다.

브라우저에서 `cache` 옵션은 가져오기 요청이 *브라우저의* HTTP 캐시와 상호 작용하는 방식을 나타냅니다. 이 확장을 사용하면 `cache`은 *서버측* 가져오기 요청이 프레임워크의 영구 [데이터 캐시](../../guides/caching.mdx#data-cache)와 상호 작용하는 방식을 나타냅니다.

서버 구성 요소 내에서 직접 `fetch` 및 `async`을 사용하여 `await`을 호출할 수 있습니다.

```tsx filename="app/page.tsx" switcher
export default async function Page() {
  let data = await fetch('https://api.vercel.app/blog')
  let posts = await data.json()
  return (
    <ul>
      {posts.map((post) => (
        <li key={post.id}>{post.title}</li>
      ))}
    </ul>
  )
}
```

```jsx filename="app/page.js" switcher
export default async function Page() {
  let data = await fetch('https://api.vercel.app/blog')
  let posts = await data.json()
  return (
    <ul>
      {posts.map((post) => (
        <li key={post.id}>{post.title}</li>
      ))}
    </ul>
  )
}
```

## `fetch(url, options)`

Next.js는 [웹 `fetch()` API](https://developer.mozilla.org/docs/Web/API/Fetch_API)을 확장하므로 [사용 가능한 기본 옵션](https://developer.mozilla.org/docs/Web/API/fetch#parameters) 중 하나를 사용할 수 있습니다.

### `options.cache`

요청이 Next.js [데이터 캐시](../../guides/caching.mdx#data-cache)와 상호 작용하는 방법을 구성합니다.

```ts
fetch(`https://...`, { cache: 'force-cache' | 'no-store' })
```

- **`auto no cache`** (기본값): Next.js는 개발 중인 모든 요청에 대해 원격 서버에서 리소스를 가져오지만 경로가 정적으로 사전 렌더링되므로 `next build` 중에 한 번 가져옵니다. [동적 API](../../guides/caching.mdx#dynamic-rendering)가 경로에서 감지되면 Next.js는 모든 요청에서 리소스를 가져옵니다.
- **`no-store`**: Next.js는 경로에서 동적 API가 감지되지 않는 경우에도 요청이 있을 때마다 원격 서버에서 리소스를 가져옵니다.
- **`force-cache`**: Next.js는 데이터 캐시에서 일치하는 요청을 찾습니다.
  - 일치하는 항목이 있고 신선한 경우 캐시에서 반환됩니다.
  - 일치 항목이 없거나 오래된 일치 항목이 있는 경우 Next.js는 원격 서버에서 리소스를 가져와 다운로드한 리소스로 캐시를 업데이트합니다.

### `options.next.revalidate`

```ts
fetch(`https://...`, { next: { revalidate: false | 0 | number } })
```

리소스의 캐시 수명(초)을 설정합니다. [데이터 캐시](../../guides/caching.mdx#data-cache).

- **`false`** - 리소스를 무기한 캐시합니다. `revalidate: Infinity`과 의미상 동일합니다. HTTP 캐시는 시간이 지남에 따라 오래된 리소스를 제거할 수 있습니다.
- **`0`** - 리소스가 캐시되지 않도록 합니다.
- **`number`** - (초 단위) 리소스의 캐시 수명이 최대 `n`초여야 함을 지정합니다.

> **알면 좋은 점**:
>
> - 개별 `fetch()` 요청이 경로의 `revalidate` 숫자를 설정하면 전체 경로 재검증 간격이 줄어듭니다.[default `revalidate`](../file-conventions/route-segment-config.mdx#revalidate) of a route, the whole route revalidation interval will be decreased.
> - 동일한 경로에서 동일한 URL를 사용하는 두 개의 가져오기 요청의 `revalidate` 값이 다른 경우 더 낮은 값이 사용됩니다.
> - Conflicting options such as `{ revalidate: 3600, cache: 'no-store' }`과 같은 충돌하는 옵션은 허용되지 않으며 둘 다 무시되며 개발 모드에서는 경고가 터미널에 인쇄됩니다.

### `options.next.tags`

```ts
fetch(`https://...`, { next: { tags: ['collection'] } })
```

리소스의 캐시 태그를 설정합니다. 그런 다음 [`revalidateTag`](revalidateTag.mdx)을 사용하여 요청 시 데이터를 재검증할 수 있습니다. 사용자 정의 태그의 최대 길이는 256자이고 최대 태그 항목은 128자입니다.

## 문제 해결

### 기본 가져오기 `auto no store` 및 `cache: 'no-store'`가 개발 중인 최신 데이터를 표시하지 않습니다.

Next.js는 더 빠른 응답과 청구된 API 호출에 대한 비용을 줄이기 위해 로컬 개발의 HMR(Hot Module 교체) 전반에 걸쳐 서버 구성 요소의 `fetch` 응답을 캐시합니다.

기본적으로 [HMR 캐시](../config/next-config-js/serverComponentsHmrCache.mdx)는 기본 `auto no cache` 및 `cache: 'no-store'` 옵션이 있는 가져오기 요청을 포함하여 모든 가져오기 요청에 적용됩니다. 즉, 캐시되지 않은 요청에는 HMR 새로 고침 사이에 최신 데이터가 표시되지 않습니다. 그러나 탐색이나 전체 페이지를 다시 로드하면 캐시가 지워집니다.

자세한 내용은 [`serverComponentsHmrCache`](../config/next-config-js/serverComponentsHmrCache.mdx) 문서를 참조하세요.

### 개발 중인 하드 새로 고침 및 캐싱

개발 모드에서 요청에 `cache-control: no-cache` 헤더가 포함되어 있으면 `options.cache`, `options.next.revalidate` 및 `options.next.tags`이 무시되고 `fetch` 요청이 소스에서 제공됩니다.

브라우저에는 일반적으로 개발자 도구에서 캐시가 비활성화되거나 강제 새로 고침 중에 `cache-control: no-cache`이 포함됩니다.
